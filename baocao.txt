PHẦN 1. THÔNG TIN TỔNG QUAN
--------------------------------------------------------------------------------
1.1. Cấu hình Dự án & Công nghệ
- Tên Project: th6 (Tên ứng dụng hiển thị: PhotoVault)
- Package Name / Application ID: com.example.th6
- Phân loại module: Module đơn (:app)
- Android Gradle Plugin (AGP): 9.3.3
- Compile SDK: 36 (Android 15 / Baklava)
- Target SDK: 35 (Android 15)
- Min SDK: 24 (Android 7.0 Nougat)
- Ngôn ngữ lập trình: Java 11 (Java-based Android app)
- Giao diện UI: XML Layouts + ViewBinding + Material Design Components 3
- Quản lý phụ thuộc: Gradle Version Catalog (gradle/libs.versions.toml) + Gradle Kotlin DSL (build.gradle.kts)
- Dịch vụ Nền tảng (Backend/Cloud):
  + Firebase Auth (BOM 33.9.0): Đăng ký, đăng nhập, quên mật khẩu, quản lý hồ sơ.
  + Firebase Firestore: Lưu trữ metadata ảnh, album, thông tin người dùng.
  + ImgBB Upload API (REST API qua OkHttp 4.12.0): Lưu trữ file ảnh thực tế trên cloud.
  + SQLite Local Database (BackupUploadLedger): Sổ cái nhật ký tạm lưu trạng thái upload ảnh.
  + WorkManager 2.9.0: Quản lý tác vụ sao lưu nền tự động (PeriodicWorkRequest & OneTimeWorkRequest).
  + Glide 4.16.0: Tải, hiển thị, cache ảnh & thumbnail.
  + androidx.media3 (ExoPlayer, UI, Transformer 1.3.1): Phát video và cắt/xuất video mp4.

1.2. Mục tiêu Ứng dụng
PhotoVault là ứng dụng quản lý thư viện phương tiện (Ảnh/Video) tích hợp điện toán đám mây. Ứng dụng kết hợp việc hiển thị thư viện cục bộ (MediaStore) với thư viện cloud (ImgBB + Firestore), hỗ trợ người dùng xem ảnh/video, tạo album, đánh dấu yêu thích, thùng rác tạm thời, trình chiếu ảnh, chỉnh sửa ảnh chuyên sâu (Crop, Draw, Rotate, Filters, Fine Adjustments), cắt/chỉnh sửa video, cũng như tự động sao lưu nền ảnh cục bộ lên đám mây thông qua WorkManager.

1.3. Tổng quan Kiến trúc Hiện tại
- Dự án chưa áp dụng kiến trúc chuẩn như MVVM hay Clean Architecture với ViewModel/LiveData/Flow.
- Kiến trúc thực tế là Event-driven / Controller-based dựa trên Activity - Fragment - Helper/Manager/Service:
  + UI Layer: `MainActivity` đóng vai trò Host Container điều hướng BottomNavigationView giữa 5 Fragment chính (`LibraryFragment`, `AlbumFragment`, `FavoritesFragment`, `TrashFragment`, `ProfileFragment`).
  + Screen Layer: Các Activity độc lập xử lý màn hình phụ (`PhotoDetailActivity`, `PhotoEditorActivity`, `VideoPlayerActivity`, `VideoEditorActivity`, `BackupCenterActivity`, `AlbumDetailActivity`, `SearchActivity`, `SettingsActivity`, `SlideshowActivity`, `LoginActivity`, `RegisterActivity`, `ForgotPasswordActivity`, `SplashActivity`).
  + Adapter Layer: `LocalPhotoAdapter`, `PhotoAdapter`, `AlbumAdapter`, `PhotoThumbnailAdapter`.
  + Data & Service Layer:
    * `FirestoreRepository`: Đóng gói toàn bộ thao tác CRUD tới Cloud Firestore.
    * `DevicePhotoScanner`: Quét MediaStore lấy danh sách ảnh/video local bất đồng bộ.
    * `ImgBBUploadService`: Đóng gói HTTP Client gửi multipart/form-data lên ImgBB REST API.
    * `PhotoBackupManager`: Tính toán giao thoa giữa MediaStore và Firestore để lập hàng đợi sao lưu.
    * `PhotoBackupWorker`: WorkManager Worker thực thi quá trình upload ảnh nền.
    * `BackupUploadLedger`: SQLite Database lưu tạm URL ảnh ImgBB đã upload thành công trước khi ghi metadata vào Firestore (chống upload lặp khi Worker bị dừng).
    * `BackupWorkScheduler`: Lập lịch WorkManager nền.

2.2. Trách nhiệm Các File Quan trọng
- `MainActivity.java`: Khởi tạo ứng dụng, kiểm tra đăng nhập để kích hoạt WorkManager, điều hướng giữa 5 Fragment chính.
- `LibraryFragment.java`: Màn hình cốt lõi của ứng dụng. Xin quyền READ_MEDIA, quét MediaStore, lấy ảnh cloud từ Firestore, thực hiện gộp (merge) hiển thị theo mốc thời gian (Tất cả/Ngày/Tháng/Năm), chế độ chọn nhiều (Multi-select), chia sẻ, đưa vào album, xóa local.
- `PhotoEditorActivity.java`: Trình chỉnh sửa ảnh nâng cao. Quản lý trạng thái Undo/Redo bằng Stack, điều chỉnh thông số màu sắc (Exposure, Brightness, Contrast, Saturation, Highlights, Shadows, Temp, Tint), áp dụng bộ lọc (Vivid, Warm, Cool, Mono, Dramatic, Fade), Cắt ảnh (CropOverlayView), Vẽ tự do (DrawingOverlayView), Xoay/Lật. Xuất ảnh lưu bản sao hoặc ghi đè (MediaStore).
- `PhotoBackupWorker.java`: Worker chạy nền của WorkManager thực hiện sao lưu ảnh tự động. Kiểm tra điều kiện, quét ảnh chưa upload, tải lên ImgBB qua `ImgBBUploadService`, ghi nhận vào SQLite `BackupUploadLedger`, sau đó lưu metadata idempotent vào Firestore (`backup_<sha256(uri)>`).
- `ImgBBUploadService.java`: Dịch vụ gửi HTTP Multipart POST lên API ImgBB (`https://api.imgbb.com/1/upload`), hỗ trợ retry lũy thừa (exponential backoff) với lỗi kết nối mạng.
- `FirestoreRepository.java`: Thực thi toàn bộ lệnh CRUD Firestore trên 3 collection: `users`, `users/{uid}/photos`, `users/{uid}/albums`.

PHẦN 3. KIẾN TRÚC CHI TIẾT
--------------------------------------------------------------------------------
3.1. Phân tầng Thành phần & Luồng Gọi Hàm
- Tầng UI / Controller (`LibraryFragment`, `PhotoDetailActivity`, `PhotoEditorActivity`, v.v.):
  Lắng nghe sự kiện tương tác người dùng, gọi `DevicePhotoScanner` để đọc dữ liệu đĩa cục bộ, gọi `FirestoreRepository` để truy vấn/cập nhật đám mây.
- Tầng Xử lý Dữ liệu Local (`DevicePhotoScanner`):
  Sử dụng `ContentResolver` truy vấn `MediaStore.Images.Media` và `MediaStore.Video.Media` trên Thread Pool riêng (`SCAN_EXECUTOR`), trả về danh sách `LocalMediaPhoto` cho Main Thread.
- Tầng Xử lý Cloud & Network (`ImgBBUploadService` & `FirestoreRepository`):
  `ImgBBUploadService` dùng `OkHttpClient` với `UriRequestBody` stream nội dung tệp trực tiếp từ `ContentResolver` tới ImgBB API. Kết quả URL được trả về cho Callback.
  `FirestoreRepository` cập nhật document tương ứng trên Firestore theo UID người dùng.

3.2. Sơ đồ Luồng Điều hướng giữa các Màn hình
- `SplashActivity` -> (Đã đăng nhập) -> `MainActivity`
- `SplashActivity` -> (Chưa đăng nhập) -> `LoginActivity`
- `LoginActivity` <-> `RegisterActivity` / `ForgotPasswordActivity` -> `MainActivity`
- `MainActivity` (Bottom Nav):
  ├── `LibraryFragment` -> `PhotoDetailActivity` / `VideoPlayerActivity` / `SearchActivity` / `BackupCenterActivity`
  ├── `AlbumFragment` -> `AlbumDetailActivity` -> `PhotoDetailActivity`
  ├── `FavoritesFragment` -> `PhotoDetailActivity`
  ├── `TrashFragment` -> `PhotoDetailActivity`
  └── `ProfileFragment` -> `SettingsActivity` / `BackupCenterActivity` / `LoginActivity` (Logout)
- `PhotoDetailActivity` -> `PhotoEditorActivity` / `PhotoInfoBottomSheetDialog`
- `VideoPlayerActivity` -> `VideoEditorActivity`

3.3. Quản lý Bất đồng bộ & Trạng thái
- Xử lý bất đồng bộ: Sử dụng Java `ExecutorService` (`Executors.newSingleThreadExecutor()`, `Executors.newFixedThreadPool(2)`) kết hợp với Android `Handler(Looper.getMainLooper())` để đẩy kết quả về UI thread.
- Trạng thái UI (Loading / Success / Empty / Error):
  + Hầu hết các màn hình dùng `ProgressBar` hiển thị trạng thái Loading.
  + Layout `layoutEmpty` (với ImageView + TextView) hiển thị khi dữ liệu rỗng.
  + Thông báo lỗi thông qua `Toast` hoặc `Snackbar` (có nút "Thử lại").

PHẦN 5. FIREBASE VÀ LƯU TRỮ
--------------------------------------------------------------------------------
5.1. Firebase Authentication
- Dịch vụ: Firebase Email/Password Auth.
- File mã nguồn: `LoginActivity.java`, `RegisterActivity.java`, `ForgotPasswordActivity.java`, `ProfileFragment.java`.
- Phương thức sử dụng: `signInWithEmailAndPassword`, `createUserWithEmailAndPassword`, `sendPasswordResetEmail`, `updateProfile`.

5.2. Firestore Data Schema
Cấu trúc Firestore thực tế đang được sử dụng trong `FirestoreRepository.java`:

- Collection: `users`
  Document ID: `{uid}`
  Fields:
  + `uid` (String)
  + `displayName` (String)
  + `email` (String)
  + `photoUrl` (String)
  + `createdAt` (long)

- Collection: `users/{uid}/photos`
  Document ID: `{photoId}` (hoặc `backup_<sha256(uri)>` đối với ảnh sao lưu)
  Fields:
  + `id` (String)
  + `ownerUid` (String)
  + `name` (String)
  + `imageUrl` (String)
  + `displayUrl` (String)
  + `createdAt` (long)
  + `favorite` (boolean)
  + `trashed` (boolean)
  + `trashedAt` (long)
  + `localMediaId` (long)
  + `localMediaUri` (String)
  + `localDateModified` (long)
  + `albumIds` (List<String>)
  + `storageProvider` (String - mặc định "imgbb")
  + `contentHash` (String - SHA-256 hash nội dung ảnh)

- Collection: `users/{uid}/albums`
  Document ID: `{albumId}`
  Fields:
  + `id` (String)
  + `ownerUid` (String)
  + `name` (String)
  + `createdAt` (long)
  + `coverImageUrl` (String)
  + `photoCount` (int)

5.3. ImgBB Storage Service
- Endpoint API: `https://api.imgbb.com/1/upload`
- Khóa API (API Key): Đã bị hardcode trực tiếp trong biến tĩnh `API_KEY` trong file `ImgBBUploadService.java`.
  * Đánh giá bảo mật: RỦI RO BẢO MẬT CAO. Khóa API nằm trực tiếp trong mã nguồn mã hóa APK, bất kỳ ai giải nén APK đều có thể lấy và lạm dụng quota ImgBB.
- Cách gửi dữ liệu: HTTP Multipart/form-data sử dụng `OkHttpClient` và `UriRequestBody` stream từ `ContentResolver`.
- Giới hạn: Tối đa 32MB / ảnh.
- Xử lý lỗi & Retry: Thử lại tối đa 3 lần (với delay 500ms, 1000ms...) khi gặp lỗi mạng ngắt kết nối hoặc HTTP status 408, 429, 5xx.

5.4. Quy tắc Bảo mật (Firebase Security Rules)
- Tình trạng: Không tìm thấy file `firestore.rules` hoặc cấu hình Security Rules trong thư mục mã nguồn project.
- Kết luận: Chưa thể xác minh quy tắc bảo mật trên Server Firebase. Cần kiểm tra cấu hình trên Firebase Console.

PHẦN 6. LUỒNG SAO LƯU VÀ ĐỒNG BỘ
--------------------------------------------------------------------------------
6.1. Sơ đồ Luồng Upload / Backup Chi tiết
[MediaStore Image]
       │
       ▼
[PhotoBackupManager]: Quét ảnh local -> Truy vấn Firestore (`users/{uid}/photos`)
       │
       ├─► Đã có trên Firestore & Modified Date khớp ──► Đánh dấu UPLOADED (Skip)
       ├─► Tìm thấy trong SQLite Ledger ──────────────► Đánh dấu METADATA_PENDING (Bỏ qua Upload ImgBB)
       └─► Chưa có ──────────────────────────────────► Đánh dấu PENDING
       │
       ▼
[PhotoBackupWorker] (WorkManager Loop):
       │
       ├─1. Lấy tệp PENDING -> Gửi `ImgBBUploadService.uploadImageWithRetry`
       │      │
       │      └─► Nhận Image URL từ ImgBB -> Ghi ngay vào SQLite `BackupUploadLedger`
       │
       ├─2. Tạo đối tượng `Photo` -> Gọi `FirestoreRepository.saveBackupPhoto()`
       │      │   (Document ID = "backup_" + SHA256(uri))
       │      │
       │      └─► Ghi Firestore Thành công -> Xóa bản ghi trong SQLite `BackupUploadLedger`
       │
       └─3. Cập nhật Progress WorkManager
       │
       ▼
[Hoàn tất Lượt Backup] -> Cập nhật `lastSyncTime` trong SharedPreferences.

6.2. Cơ chế Chống Lặp & Đảm bảo Tính Toàn vẹn (Idempotency)
- Tầng Firestore: Document ID được cố định bằng chuỗi `backup_` + SHA-256 Hash của URI local. Do đó nếu ghi đè lại cùng tệp, Firestore sẽ tự `set` cập nhật chứ không tạo Document trùng lặp.
- Tầng SQLite Ledger: Nếu ứng dụng bị ngắt đột ngột giữa chừng (sau khi ImgBB trả về URL nhưng trước khi ghi Firestore thành công), ở lần chạy sau `PhotoBackupManager` sẽ phát hiện bản ghi trong SQLite `BackupUploadLedger` và khôi phục URL, không tốn băng thông upload lại ImgBB.

6.3. Điểm Yếu / Khoảng trống Trong Luồng Đồng bộ
- Không hỗ trợ Video Backup: Tệp video bị bỏ qua hoàn toàn trong luồng sao lưu.
- Thiếu Real-time Listener: Ảnh do thiết bị khác upload sẽ không tự hiện lên thiết bị này cho đến khi người dùng làm mới dữ liệu thủ công.
- URI Local khác thiết bị: Khi người dùng đăng nhập tài khoản trên thiết bị B, metadata từ Firestore có `localMediaUri` của thiết bị A (không tồn tại trên thiết bị B). Hệ thống xử lý đúng bằng cách hiển thị tile Cloud, tuy nhiên nếu bấm mở ảnh gốc sẽ tải qua URL Cloud chứ không tải lưu lại vào MediaStore thiết bị B.

PHẦN 8. LỖI VÀ RỦI RO (BUGS & RISKS)
--------------------------------------------------------------------------------
[CRITICAL] RISK-001: Lộ Khóa API ImgBB Trong Mã Nguồn
- Bằng chứng: `ImgBBUploadService.java` chứa dòng mã `private static final String API_KEY = "57396217bacb8f9d07321ce100a5df6e";`
- Tác động: Khóa API có thể bị trích xuất dễ dàng từ file APK giải nén. Kẻ xấu có thể dùng API Key này để tải tài nguyên rác làm kiệt quệ tài khoản/quota ImgBB của ứng dụng.

[CRITICAL] RISK-002: Chưa Xác minh Quy tắc Bảo mật Firebase Security Rules
- Bằng chứng: Trong project không có file `firestore.rules`.
- Tác động: Nếu trên Firebase Console chưa cài đặt Security Rules (đang để mode Test công khai), bất kỳ ai có Firebase Config đều có thể đọc/xóa toàn bộ cơ sở dữ liệu Firestore của tất cả người dùng.

[HIGH] BUG-001: Lỗi Render Bất đồng bộ trong PhotoEditorActivity Khi Bị Đóng
- Bằng chứng: `PhotoEditorActivity.java` sử dụng `renderExecutor` để xuất ảnh ở hàm `saveEditedImage()`. Glide `FutureTarget.get()` chạy blocking trên Thread Pool. Nếu Activity bị ngắt/destroy đột ngột trong khi đang render, handler post back hoặc context ứng dụng có thể gặp lỗi rò rỉ bộ nhớ hoặc NullPointer.
- Tác động: Nguy cơ crash ứng dụng khi người dùng bấm Lưu rồi lập tức đóng Activity.

[HIGH] BUG-002: Lỗi Thiếu Real-time Sync Đa Thiết Bị Trên Firestore
- Bằng chứng: `FirestoreRepository.java` sử dụng `.get()` một lần cho mọi truy vấn thay vì `.addSnapshotListener()`.
- Tác động: Khi hai thiết bị cùng đăng nhập một tài khoản, hành động xóa/thêm/sửa album hay ảnh ở thiết bị A không được cập nhật tức thì sang thiết bị B.

[MEDIUM] BUG-003: Tính năng Sao lưu Bỏ qua Tệp Video
- Bằng chứng: `PhotoBackupWorker.java` có câu lệnh `if (local.isVideo()) continue;` và `DevicePhotoScanner.scanImages()` chỉ quét ảnh.
- Tác động: Ứng dụng không sao lưu video local lên cloud dù giao diện thể hiện là "Sao lưu toàn bộ thư viện".

[MEDIUM] BUG-004: Thùng Rác Xóa Vĩnh Viễn Không Xóa Tệp Thực Trên ImgBB
- Bằng chứng: `TrashFragment.java` gọi `repository.deletePhoto()`, chỉ xóa Document trong Firestore.
- Tác động: Tệp ảnh thực tế đã upload vẫn nằm trên máy chủ ImgBB, gây lãng phí dung lượng storage và không xóa hoàn toàn dữ liệu.

[MEDIUM] BUG-005: Tiêu tốn Bộ nhớ (OOM Risk) Khi Xử lý Ảnh Kích thước Rất Lớn
- Bằng chứng: `BitmapEditor.java` tạo các Bitmap `ARGB_8888` cùng kích thước ảnh gốc cho mỗi thao tác điều chỉnh màu sắc/bộ lọc.
- Tác động: Trên các thiết bị cấu hình yếu hoặc khi chỉnh sửa ảnh camera 48MP/108MP, ứng dụng có nguy cơ gặp sự cố `OutOfMemoryError`.

[LOW] BUG-006: Chưa Có Cơ chế Phân Trang (Paging/Pagination)
- Bằng chứng: `DevicePhotoScanner.java` và `FirestoreRepository.java` nạp toàn bộ danh sách phương tiện vào `List` một lần.
- Tác động: Gây giật lag nhẹ (UI jank) khi thư viện thiết bị có trên 5.000 đến 10.000 ảnh.

PHẦN 11. TỪ ĐIỂN DỮ LIỆU VÀ THUẬT NGỮ
--------------------------------------------------------------------------------
11.1. Các Trạng thái Backup của LocalMediaPhoto
- `STATUS_PENDING` ("PENDING"): Tệp local chưa được sao lưu lên Cloud.
- `STATUS_UPLOADING` ("UPLOADING"): Tệp đang trong quá trình upload ImgBB.
- `STATUS_UPLOADED` ("UPLOADED"): Tệp đã upload ImgBB và đã ghi nhận metadata vào Firestore.
- `STATUS_FAILED` ("FAILED"): Tiến trình sao lưu bị lỗi.
- `STATUS_METADATA_PENDING` ("METADATA_PENDING"): Ảnh đã upload xong lên ImgBB (đã lưu URL vào SQLite `BackupUploadLedger`) nhưng chưa ghi xong vào Firestore.

11.2. Đặt tên Document ID trong Firestore
- User Document: Document ID = Firebase Auth User UID (`user.getUid()`).
- Cloud Photo Document: Document ID = Auto UUID hoặc `backup_` + SHA256(localContentUri).
- Album Document: Document ID = Auto UUID (`UUID.randomUUID().toString()`).
